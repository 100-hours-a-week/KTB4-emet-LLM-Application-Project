# F. 반복 요청 시 중복 방지 (신규 기능) — 구현 및 테스트 결과

E-50번에서 "같은 재료로 반복 요청하면 거의 같은 요리가 다시 나온다"는 실제 기능 갭이 발견되어 신규 구현한 기능의 전체 기록.

## 배경

> "아무래도 매번 같은 질문에 같은 답변을 내리는건 음식에 대해서 아닌것같아. 어느날 보니 같은 재료를 가지고있는데 그때와 다른 음식 먹고싶을텐데 그때마다 동일한 음식과 레시피를 보여주는건 아니라고 생각해"
>
> "RAG에 의한 레시피는 항상 같은게 나오는게 맞아 하지만 사용자가 재요청할 수 있으니 그때를 대비해서 다른 요리 레시피를 요구하면 RAG와 프리뷰레시피를 제외한 요리를 재검색 및 프리뷰 생성하고 싶어. 그 과정에서 만약에 이전 RAG에서 적합한데 후순위로 밀린 레시피가 있다면 검색수를 줄이고 이전 보여주지않은 예비 레시피로 계산하고싶어"

즉:
- 같은 재료로 첫 요청 시 RAG 결과는 결정적(항상 동일)인 게 맞음 — 이건 바꾸지 않음
- 재요청("다른 거 없어?") 시엔 이미 보여준 RAG+생성 레시피를 전부 제외하고 재검색/재생성
- 이전에 RAG에서 적합했지만 순위(top 4)에 밀려 못 보여준 레시피가 있으면, 그걸 우선 백업으로 쓰고 LLM 생성 개수를 그만큼 줄임

## 구현

| 파일 | 변경 내용 |
|---|---|
| [states.py](../states.py) | `shown_rag_ids: List[str]`, `shown_titles: List[str]` 필드 추가 (대화 내내 누적, `finalized_recipes`와 동일 패턴 — 별도 reducer 없이 노드가 직접 이어붙여서 반환) |
| [nodes/preview_recipes.py](../nodes/preview_recipes.py) | `evaluate_rag_options`에 `exclude_ids` 파라미터 추가 — 이미 보여준 recipe_id는 적합 판정 후보에서 제외. `preview_recipe_options`가 `shown_titles`를 누적하고, LLM 생성 시 `excluded_titles`에 이번 턴 RAG 옵션 제목 + 지금까지 보여준 전체 제목을 합쳐서 전달 |
| [nodes/nodes.py](../nodes/nodes.py) | `rag_adequacy_check`가 `shown_rag_ids`를 읽어서 재검색 후보에서 제외하고, 새로 채택된 recipe_id를 다시 누적해서 반환 |

핵심 원리: RAG 검색 자체는 같은 재료면 매번 결정적으로 같은 12개 후보를 반환하므로, 굳이 전체 순위를 기억할 필요 없이 "이미 보여준 id만 걸러내면" 이전에 순위에 밀렸던 레시피가 자연스럽게 다음 순위로 올라옴.

## 1차 검증 — 단위 테스트 (LLM 없음, 합성 데이터)

**RAG 백업 풀 동작 확인**: 6개의 적합 RAG 후보(id 1~6) 중 PREVIEW_TOTAL_COUNT(4)만 우선 채택되는 상황을 시뮬레이션.

| 회차 | 채택된 recipe_id | shortfall |
|---|---|---|
| 1회차 | `['1', '2', '3', '4']` | 0 |
| 2회차 (shown_rag_ids=[1,2,3,4] 이어받음) | `['5', '6']` | **2** (4→2로 감소) |

→ 이전에 밀렸던 5,6번이 정확히 다음 순위로 채택되고, LLM 생성 개수(shortfall)가 자동으로 줄어드는 것 확인.

**제목 누적 확인**: mock LLM으로 `preview_recipe_options`를 2회 호출해서 실제 프롬프트 텍스트를 캡처.
- 2회차 프롬프트에 `제외할 요리 이름 목록(excluded_titles): ['RAG레시피1', '생성레시피A']`로, RAG+생성 제목이 정확히 누적되어 들어감을 실제 프롬프트 텍스트로 직접 확인.

정적 검증(`py_compile`, `graph.build()`)도 정상.

## 알려진 한계

3개 재료짜리 조합 위주라 대부분 RAG 적합 후보가 0~1개뿐이었음(실제 레시피는 보통 재료가 더 많이 필요해서 3개만으로는 RAG 점수제 통과가 어려움). 그래서 이번 배치는 "RAG 백업 풀에서 밀린 레시피가 다음 라운드에 채택되는지"는 99, 100번에서만 살짝 확인됐고(rag_count 1→0으로 소진), 대부분은 순수 LLM 생성 쪽 중복 방지만 검증됨. RAG 백업 풀 동작을 더 확실히 보려면 재료 5~6개 이상인 케이스를 추가로 테스트하는 게 좋음 (미실행).
