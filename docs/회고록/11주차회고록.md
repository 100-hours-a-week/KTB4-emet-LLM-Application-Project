## 금주 최신화 정보
### 1. 설계

#### 1-2.현재 개발된 플로우 차트 (ver_0.2)
- 지난주의 플로우차트 초안을 재검토하고, 보완함
- Claude를 이욜해서 전체적인 플로우 차트 생성

### 2. 개발 진행상황
#### 2.1. 멀티턴 도입
  - 멀티턴을 위해서 thread_id와 체크포인터 추가
#### 2.2. 추출한 재료 분석
  - 식용 가능 여부, 재료들의 조합, 재료로 요리레시피가 생성가능한지 판단
  - 레시피 생성 가능/ 추가 재료로 레시피 생성가능 / 레시피 생성 불가능 정보 리턴
  - 추가 재료로 레시피 생성 가능하다면 최소한으로 추가하는 재료 리스트 같이 생성
#### 2.3. 예비 선택 레시피 생성
  - 추출한 재료와 예비 선택지(프리뷰 레시피) 생성
  - 예비 선택지(프리뷰 레시피): "예비요리이름"과 "추가재료리스트" 정보를 가짐
#### 2.4. RAG 예비 레시피 변환
  - 차집합(추출재료-RAG재료)을 구해서 예비 선택지(프리뷰 레시피)형태로 추출
#### 2.5.선택지 통합 응답
  - 2.4와 2.5의 결과를 합쳐서 예비 선택지(프리뷰 레시피) 리스트 생성, 추가재료가 적은순으로 나열해서 사용자에게 응답
#### 2.6.질의 분석
- 새로운 타입 "레시피 선택" 추가
  - 사용자와 재료추출과정을 거쳐서 프리뷰레시피 정보를 가진상태에서, 레시피 선택에 대한 내용이라면 해당 방향(흐름)으로 진행
#### 2.7. 레시피 선택
- 1) 초기 구현: 번호 일치 -> 요리이름 일치 -> LLM 순으로 프리뷰 레시피를 선택하도록 구현
  - 구현 이유: LLM 의존도를 줄여서 토큰 비용과 시간 비용을 줄이기 위해 구현
  - 문제점: 해당 방식은 복합적 질의를 받았을때 질의 분석에서 "레시피 선택"으로 인식하고 레시피 선택노드로 넘어오면 번호 일치와 요리이름 일치에서 맨앞요리(처음 매칭된 요리)를 선택해서 응답
    - 예)   "2번 말고 3번으로 할께", "게살볶음밥과 돼지고추장비빔밥 먹고싶어" -> 2번 레시피 출력, 게살볶음밥 레시피 출력
- 2) 최종 구현: LLM이 자체적으로 판단하도록 구현(번호일치와 요리이름 일치 삭제)
  - 예상하지못한 장점: 선택지의 요리이름중 사용자가 축약한 요리도 자체적으로 판단해서 알려줌
    -  예) "쏘야볶 알려줘" -> 소세지 야채 볶음 레시피 출력
#### 2.8. 레시피 생성
- 레시피 선택에서 이전 예비선택지 생성의 요리를 골랐다면 진행, 요리이름과 재료(추출+추가)를 기반으로 정형화된 레시피 생성하고 사용자에게 응답
#### 2.9. 레시피 재조회 출력
- 레시피 선택에서 RAG 레시피를 골랐다면 진행, RAG 레시피 정보를 사용자에게 응답

## 회고
- 이번주 처음으로 스크랩 기능을 제외한 메인 기능들 구현에 클로드 코드를 이용해서 구현을 했습니다. 사용이유는 현저히 느린 개발속도(개발진행 중에 변화하는 흐름과 기능확장)입니다. 클로드 코드가 생성한 코드들은 코드에 합병해서 실행시키지 않고 직접 검토하고 의문점은 클로드에게 질문하여 수정하거나 직접 수정하는 방식으로 진행해서 기존보다 개발속도를 많이 높였습니다. 그래서 지난주 계획보다 더 많은 개발진척을 보였습니다.
- 현재는 "흐름개선의 버그"와 "루프백" 추가를 제외하고는 기본적인 개발이 완성됬기에 현재 정적인 그래프 구조에서 동적인 (멀티)에이전트로 구성을 한번 시도했습니다. 클로드와 여러차례대화하고 인터넷 검색을 통해서 멀티에이전트로의 변환이 현재 구현한 노드들이 많아 이부분들을 툴로 치환하고 새로운 툴 몇개만 추가하면 에이전트화에 어렵지 않다는 결론을 내렸습니다. 하지만 이는 현재 이론뿐이기에 일단 먼저 차주 목표를 우선순위대로 1~3을 진행한 후, 지인들에게 베타테스트를 위해서 프론트엔드 구현을 계획중입니다.
