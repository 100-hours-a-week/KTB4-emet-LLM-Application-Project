## 1. 코드 버그 수정 (`bugfix/guard` → `main`)

이전 세션에 테스트케이스를 설계하면서 찾아뒀던 문제들을 순서대로 처리.

### 1) `retreiver_recipes` IndexError 방지 + `select_recipe_option` 번호 불일치

- `nodes/ingredients.py`의 `apply_ingredient_modification`: `existing_names` 집합이 루프 진입 전 1회만 계산돼서, 한 발화 안에 동의어 재료 두 개가 같이 들어오면(`"계란이랑 달걀 있어"`) 중복 제거가 안 됐음.

- 두 경로가 공유하는 `_merge_deduped` 헬퍼로 통합, 항목을 하나씩 추가하며 집합을 갱신하도록 수정.

### 3) 특수재료 게이트 정규화

- `nodes/preview_recipes.py`의 `evaluate_rag_recipe`: `SPECIALTY_INGREDIENTS`(랍스터, 캐비어 등)와 raw 문자열로 비교하고 있어서, 다른 모든 비교 지점과 기준이 달랐음. `normalize_ingredient_name()`을 거치도록 통일.
- 현재는 등록된 동의어가 없어 실제 판정 결과는 안 바뀌지만, 표기 변형이 사전에 추가될 때를 대비한 방어 코드.

### 4) 궁합 경고 시스템 오탐/미탐 3건

- **오탐**: `ingredient_categories.py`에서 "우유" 라벨이 `CALCIUM` 태그에 매핑돼 있어서, 두부/멸치/미역처럼 칼슘 태그를 가진 아무 재료나 매운 음식과 같이 있으면 "매운 음식+우유" 경고가 떴음. `CALCIUM`과 분리된 `MILK` 태그를 새로 만들어 분리.
- **미탐 → 변질**: `food_combination_matcher.py`에서 "특정 약물/조합"처럼 재료 카테고리로 표현 불가능한 라벨이 규칙에 섞여 있으면 그 라벨만 빼고 나머지로 판정하고 있었음. "티라민 함유 발효식품 + 특정 약물" 규칙이 사실상 "티라민 식품 2개"라는 다른 조건으로 조용히 변질돼 있던 것. 매핑 안 되는 라벨이 하나라도 있으면 규칙 전체를 평가하지 않도록 수정.
- **미탐**: 궁합 쌍 매칭(`check_pair_taboo`)이 `HYPERNYM_MAP`(상위/하위 개념)을 안 써서 "묵은지"가 "김치" 궁합 규칙에 안 걸렸음. 방향성 없는 동일성 비교용 `_normalize_for_taboo` 헬퍼 추가.
- BENZOATE_PRESERVATIVE 태그를 가진 재료가 하나도 없어 안식향산나트륨 규칙이 dead rule인 문제는 식품학적 판단이 필요해 이번 범위에서 의도적으로 제외.

### 5) S3 동기화 순서 + 불필요한 재업로드

- `main.py`: `import graph`가 파일 최상단에 있어서, `sync_vdb_from_s3()`(다운로드)보다 먼저 실행돼버리는 문제. `import graph`를 `lifespan` 안, 다운로드 호출 다음으로 이동.

## 2. 빌드 파이프라인 개선

### GitHub Actions 캐시 미설정 → 매 배포마다 임베딩 모델 재다운로드

`docker/build-push-action@v5`에 `cache-from`/`cache-to` 설정이 없어서, GitHub Actions 호스트 러너(매번 새 VM)가 이전 빌드의 Docker 레이어를 전혀 재사용하지 못하고 있었다. Dockerfile 주석은 "소스코드만 바뀌면 캐시됨"이라고 돼 있었지만 이건 로컬 빌드에만 해당하는 얘기였고, CI에서는 코드 변경 여부와 무관하게 BGE-m3(~2.2GB)를 매번 처음부터 다시 받고 있었다.

**수정**: `cache-from: type=gha`, `cache-to: type=gha,mode=max` 추가.

## 3. 가장 큰 발견 — 리눅스 이미지에 CUDA 툴킷 전체가 통째로 설치되고 있었음

배포 중 EC2에서 반복적으로 `no space left on device`가 발생해서 원인을 추적한 결과:

```
docker system df -v
IMAGE  SIZE 16.4GB  SHARED SIZE 0B  UNIQUE SIZE 16.37GB
```

이미지 하나가 16.4GB. `uv.lock`을 확인해보니 `torch`가 리눅스에서 다음을 통째로 끌고 오고 있었다:

```
cuda-bindings, cuda-toolkit[cublas, cudart, cufft, cufile, cupti, curand,
cusolver, cusparse, nvjitlink, nvrtc, nvtx], nvidia-cudnn-cu13,
nvidia-cusparselt-cu13, nvidia-nccl-cu13, nvidia-nvshmem-cu13, triton
```

이 프로젝트는 임베딩을 항상 `device="cpu"`로만 쓰는데(GPU 없는 EC2 배포), 전체 NVIDIA CUDA 런타임이 순수하게 죽은 용량으로 들어가 있었던 것.

**수정** (`pyproject.toml`):

```toml
[tool.uv.sources]
torch = [
  { index = "pytorch-cpu", marker = "sys_platform == 'linux'" },
]

[[tool.uv.index]]
name = "pytorch-cpu"
url = "https://download.pytorch.org/whl/cpu"
explicit = true
```

**삽질 포인트**: `tool.uv.sources`는 **간접 의존성에는 적용되지 않았다.** `torch`가 `sentence-transformers`를 통해서만 들어오는 간접 의존성인 동안에는 이 오버라이드가 계속 무시됐고, `torch`를 `[project.dependencies]`에 직접 명시하고 나서야 적용됐다. 처음에 `rm uv.lock && uv lock`으로 전체 재생성을 시도했다가 관련 없는 패키지 10여 개가 같이 버전이 올라가버려서, `uv lock --upgrade-package torch`로 범위를 좁혀 다시 진행했다.

결과: `cuda-toolkit`, `nvidia-*`, `triton` 전부 제거. macOS 등 다른 플랫폼은 원래대로 일반 PyPI 배포판 사용.

## 4. 배포 트러블슈팅 타임라인

1. **`bugfix/guard` 생성 → 7개 커밋 → `test/betatest`에 강제 push로 완전 덮어쓰기 → `main`으로 fast-forward 머지 → push** — `main` push가 `deploy.yml` 트리거 조건과 일치해 자동 배포 시작.
2. **1차 배포 실패**: `docker pull` 도중 `no space left on device` (scipy 라이브러리 추출 중). `set -e`가 정상 작동해서 워크플로우는 실패로 표시됐고, 기존 컨테이너는 안 건드려짐 — 다만 이때는 미처 몰랐던 문제가 이미 있었음(4번 참고).
3. **디스크 진단**: `docker image prune -f`는 261MB만 회수. `docker system df -v`로 이미지 하나가 16.4GB인 걸 확인 → CUDA 툴킷 문제 발견 및 수정(위 3번) → 커밋·push.
4. **서비스가 22시간째 다운돼 있던 걸 발견**: `docker ps -a`에서 `chatbot-container`가 `Exited (143)`(= `docker stop`에 의한 정상 종료) 상태로 22시간째 멈춰 있었음. 오늘 배포 실패는 `set -e` 때문에 `stop`까지 가지도 못했으니, 이건 **더 이전의(오늘 `set -e` 추가 전) 실패한 배포가 컨테이너를 멈춰놓고 재생성에 실패한 채 방치된 것**으로 추정. `docker start`로 즉시 복구.
5. **2차 배포 실패**: CUDA는 빠졌는데도 여전히 `no space left on device` (이번엔 BGE-m3 모델 캐시 레이어). `docker system df`에서 여전히 옛날 16.4GB CUDA 이미지가 컨테이너에 물려 있어서 지워지지 않고 있었던 게 원인. 컨테이너를 `stop`하고 이미지를 강제로 `rmi`해서 16GB 가까이 확보한 뒤 워크플로우 재실행 → **성공**.
6. **`.env` 동기화 삽질**: EC2에서 `.env`를 수정했는데 `docker restart`로는 반영이 안 됨 — `docker restart`/`docker start`는 컨테이너를 생성할 때 지정한 `--env-file`을 다시 읽지 않는다(이 세션에서 여러 번 반복된 패턴). 완전 재생성(`stop`→`rm`→`run`)이 필요.
7. **`/home/ubuntu/.env` vs 프로젝트 디렉토리의 `.env` 혼동**: `docker run` 커맨드가 `--env-file /home/ubuntu/.env`로 고정돼 있어서, 컨테이너는 오직 이 경로만 읽는다. git 체크아웃해둔 프로젝트 폴더 안의 `.env`는 컨테이너와 무관한 별개 파일 — 거길 고쳐도 반영 안 됨. 최종적으로 `/home/ubuntu/.env`를 직접 수정하고 재생성해서 해결.

## 5. 운영 시 기억해둘 것

- **`docker restart`/`docker start`는 `--env-file`을 다시 읽지 않는다.** `.env` 값을 바꿨으면 반드시 `stop` → `rm` → `run`으로 완전히 재생성해야 함.
- **컨테이너가 실제로 읽는 `.env`는 `/home/ubuntu/.env` 하나뿐.** 프로젝트 git 디렉토리 안의 `.env`는 관련 없음.
- **`.env`는 `.gitignore`/`.dockerignore`에 모두 포함**돼 있어서 git으로 배포되지 않는다. 로컬 Mac과 EC2의 `.env`는 서로 독립된 파일이라 값이 다르면 수동으로 맞춰야 함.
- **`deploy.yml`의 `docker image prune -f`는 pull 전에 실행**되므로, 이번 배포에서 막 dangling이 된 이미지는 다음 배포 때 정리된다 — 정상 상태에서도 "태그된 이미지 1개 + dangling 1개" 정도는 항상 있을 수 있음.
- 이번에 EC2 상의 `AWS_SECRET_ACCESS_KEY`가 진단 명령 출력 중 실수로 노출된 적이 있어 로테이션을 권고했음 — 이후 세션에서 확인 필요.

## 6. 남은 이슈

- **BENZOATE_PRESERVATIVE 태그 dead rule**: 안식향산나트륨 규칙에 걸릴 재료가 하나도 없음. 어떤 재료에 태그를 붙일지는 식품학적 판단이 필요해 보류.
- **containerd ingest 잔해**: 실패한 pull이 반복되면 `docker image prune`으로 안 지워지는 부분 다운로드 잔해가 `/var/lib/containerd/io.containerd.content.v1.content/ingest`에 쌓일 수 있음. 이번엔 확인 결과 문제 없었지만(4.0K), 주기적으로 체크할 가치는 있음.
- **EC2 디스크(28GB)가 여전히 빠듯할 가능성**: CUDA 제거로 여유가 크게 생겼지만, 이미지 크기가 다시 커질 경우(의존성 추가 등) 동일한 문제가 재발할 수 있음. 필요 시 EBS 볼륨 확장 고려.
