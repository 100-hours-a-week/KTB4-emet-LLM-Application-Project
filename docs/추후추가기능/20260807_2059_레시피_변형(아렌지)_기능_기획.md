# 추후 추가 기능 기획 — 최종 레시피 재료 변형(아렌지)

**작성 일시: 2026-08-07 20:59 (KST)**

**상태**: 논의/설계 단계. 코드 미반영.

## 기능 개요

최종 확정된 레시피(`finalize_recipe`/`fetch_rag_recipe`로 완성된 레시피)에 대해, 사용자가
특정 재료를 추가/제거/변경해서 **같은 요리를 살짝 어레인지한 버전**을 다시 받을 수 있게 하는 기능.
예: "된장찌개인데 두부 빼고 대신 감자 더 넣어줘" → 요리 이름/정체성은 유지하면서 재료 구성만 바뀐
새 레시피를 생성.

## 왜 지금 하지 않았나 (기존 흐름과의 차이)

기존에 이미 있는 "재료 목록" 변경 기능(`extract_ingredient_update`)은 **레시피를 고르기 전** 단계,
즉 "지금 가진 재료가 뭔지"를 바꿔서 추천 후보 자체를 다시 계산하는 기능임. 이번에 논의한 기능은
**이미 요리를 고르고 완성 레시피까지 받은 뒤**, 그 완성된 레시피 자체를 재료 단위로 변형해달라는
요청이라 완전히 다른 흐름 — 지금은 이 케이스를 처리하는 경로가 없음.

## 실현 가능성 — 이미 있는 것

- `structured_recipe`(`states.py`) 필드에 최종 확정된 레시피(재료/분량/조리순서)가 이미 저장돼 있고,
  다음 턴에도 초기화되지 않고 그대로 남아있음 → "변형할 원본"을 새로 만들 필요 없이 바로 활용 가능
- `finalize_recipe`의 프롬프트 패턴(`recipes_prompts.finalize_from_preview_prompt`)을 재사용해서,
  원본 레시피 + 변경 요청을 넣고 새 `StructuredRecipe`를 생성하는 새 노드를 유사하게 만들 수 있음

## 필요한 변경 (설계 초안)

1. **새 `query_type`** (예: `'레시피 변형'`) — `templates/analysis_prompts.py`의 `query_prompt`에 추가.
   "빼줘/추가해줘/바꿔줘"류 발화가 재료 목록 재계산(`레시피 추천`)이 아니라 완성 레시피 변형 요청임을
   구분해야 함.
2. **새 노드** (예: `arrange_recipe`) — `structured_recipe`(원본) + 사용자 요청을 받아 새
   `StructuredRecipe`를 생성하는 LLM 호출 1회.
3. **그래프 라우팅** — `query_analysis` → (신규 조건부 분기) → `arrange_recipe` → END.

## 핵심 난제: "재료 목록 변경"과의 모호성

"계란 빼줘" 같은 발화는 문맥 없이는 두 가지로 다 해석 가능함:
- 재료 목록에서 빼고 추천 후보를 다시 계산해달라는 것(`레시피 추천`)
- 방금 완성된 레시피에서 빼달라는 것(`레시피 변형`, 이번 기능)

### 조사 결과 — 기존 문맥 메커니즘의 한계

`query_analysis`가 참고하는 `recent_context`는 `state["messages"]`로 만들어지는데, 실제 코드를
확인해보니 **`present_recipe_options` 노드만 `messages`를 채우고 있음**. `finalize_recipe`,
`fetch_rag_recipe`, `respond_infeasible` 등은 `messages`에 아무것도 안 남김. 즉 "방금 레시피가
완성됐다"는 사실이 `query_analysis`가 보는 텍스트 문맥에는 반영되지 않는 구조적 공백이 있음.

다행히 `structured_recipe`는 텍스트 문맥과 무관하게 state에 그대로 남아있어서, "지금 변형 가능한
레시피가 있는가"는 LLM 판단 없이 이 필드의 존재 여부만으로 결정적으로 알 수 있음.

### 제안 — 명시적 되물음(clarification) + 전용 state 플래그

1. `query_analysis`가 재료 변경성 발화를 감지했는데 `structured_recipe`도 있고 재료 목록 기반
   추천 문맥도 같이 있어서 모호하면, 바로 추측하지 않고 **되물어서** 턴을 끝냄
   (예: "방금 보여드린 [요리명]을 수정해달라는 말씀이세요, 아니면 재료 목록부터 다시
   추천받고 싶으신 거예요?")
2. 다음 턴의 답변을 정확히 해석하기 위해, `recent_context` 텍스트에 의존하는 대신
   **전용 state 필드**(예: `pending_clarification: str | None`)를 새로 두고, 되물을 때 이 값을
   세팅. 다음 턴이 들어오면 일반 분류 전에 이 플래그부터 확인해서, 있으면 "레시피 변형 vs
   재료 재추천" 이지선다로 좁혀서 해석하고 플래그를 지움.
3. 이 방식이 `recent_context`에만 의존하는 것보다 안정적일 것으로 예상 — 답변 해석 범위가
   좁아서 LLM이 헷갈릴 여지가 적음.

## 아직 정해지지 않은 것 (구현 전 결정 필요)

- **모호성 해석 방식**: 위 state 플래그 방식 vs `recent_context`에 되물음 내용을 잘 남겨서 LLM이
  문맥으로 풀게 하는 방식 — 트레이드오프 비교 필요
- **애매한 답변 처리**: 되물었는데 사용자가 "아무거나"처럼 여전히 애매하게 답하면 어떻게 할지
  (기본값으로 폴백? 한 번 더 물어볼지?)
- **요리 이름 표기**: 변형본도 원래 이름을 그대로 쓸지, "된장찌개(응용)"처럼 구분 표시를 붙일지
- **RAG 출처 레시피 변형 시 출처 표기**: 원본이 RAG(실제 사이트) 출처였는데 변형하면 더 이상 그
  사이트의 정확한 레시피가 아니게 됨 — 출처 표기를 어떻게 바꿀지("원본: OO 기반 응용"으로 변경,
  또는 아예 제거)
- **캐싱 여부**: `finalize_recipe`처럼 `finalized_recipes` 캐시에 변형본도 같이 저장할지, 매번
  새로 생성할지

## 예상 작업 규모

이전에 추가한 "요리 이름 직접 검색" 흐름(`search_by_name` 등, 새 query_type 1개 + 새 노드
4~5개)과 비슷하거나 조금 작은 규모 — 새 query_type 1개 + 새 노드 1~2개(`arrange_recipe`,
필요시 되물음 처리용 노드) + 프롬프트 신규 작성.
