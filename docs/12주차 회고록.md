### 2. 개발 진행상황
#### 2.1. 재료 변경 처리 (기존 재료 추출 방식 확장)
- 사용자가 재료를 추가/제거/교체하려는 의도를 구분해서 처리하도록 확장
- 판단 결과: initial(최초 입력) / add(추가) / remove(제거) / replace(교체)
- 판단과 동시에 이전 턴의 예비 선택지 목록을 초기화하도록 처리
   - 연속으로 레시피 추천을 여러 번 요청할 때 이전 턴 선택지가 섞이던 버그 해결
- action이 remove인 경우와 그 외(initial/add/replace)인 경우를 나눠서 재료 추출
   - remove 전용 추출 노드를 별도로 구현 (제거하고 싶은 재료명만 인식)
- 두 추출 결과를 실제 재료 목록에 반영하는 단계는 LLM 호출 없이 순수 코드로 처리
   - 판단(add/remove/replace)은 LLM, 실행(리스트 병합·제거)은 코드로 역할 분리

#### 2.2. 재료 분석 결과 확장 - 불가 사유 응답
- 기존에는 "생성 불가" 판정 시 이유 없이 미개발 기능 응답으로 처리되던 것을 개선
- 판정 결과에 이유(reason) 필드 추가
   - 재료 수 부족 / 재료 조합이 요리로 성립하지 않음 / 특수 재료 필요 / 먹을 수 없는 재료 포함 등
- 전용 응답 노드 분리
   - "생성 불가"를 더 이상 미지원 기능 응답과 같은 경로로 처리하지 않음
   - 이유를 포함한 정상 응답으로 처리한 뒤 다음 질의를 받는 흐름으로 변경

#### 2.3. 음식 궁합 경고 기능 추가
- 전통적으로 궁합이 안 좋다고 알려진 재료 조합을 감지해서 안내
- 근거가 불충분한 속설(예: 두리안+술, 토마토+설탕)은 별도로 분류해서 오경고 방지
- LLM 호출 없이 순수 코드 매칭으로 구현 (재료 분석 노드 내부에 추가, 비용 부담 없음)

#### 2.4. 재료명 정규화 사전 구축
- 같은 재료를 다르게 부르는 경우(유사어/동의어)(예: 계란/달걀)와 상위/하위 개념(예: 사과/청사과)을 하나로 인식하도록 사전 기반 정규화 도입
   - {"계란", "달걀", "에그"} -> "계란" 으로 치환 
   - {"케첩", "케챱", "케찹", "토마토케첩"} -> "케첩" 으로 치환
- 부족 재료 계산, 재료 추가/제거 판단 양쪽에 공통 적용

#### 2.5. 현재 보유 재료 목록 표시
- 매 응답에 현재까지 파악된 재료 목록을 함께 보여주도록 개선
- 여러 턴에 걸친 대화 중 사용자가 현재 상태를 쉽게 파악할 수 있도록 함

## 회고
- 이번 주는 기능 개발 보다는 인프라 확장을 중점으로 진행했다. 서비스 테스트 운영을 위해서 처음으로 도메인도 구매하고, EC2 퍼블릭 도메인을 세팅했다. 그리고 vdb 업데이트 과정에서 레시피를 스크래핑하고 정형화하는 과정이 EC2에서 CPU 및 네트워크 부하가 발생할것이라고 예상했다. 그래서 중간 적재소역할로 S3에 vdb 업로드하고, 필요할때 맥에서 vdb를 갱신하고, EC2가 (재)시작할때 vdb를 S3에서 다운로드하도록 구성했다.
- 레시피를 확인하던중 "계란 달걀 샌드위치"라는 레시피가 있었는데 이처럼 유사어(동의어)에 대한 제어를 어디에서도 하지않았다. 그래서 유사어/동의어 사전파일을 개별로 만들어서 재료추출과정에서 추출한 재료들은 직접 이들 재료와 비교하여 치환해서 정규화하도록 만들었다. 이와 비슷하게 재료 조합 검토 기능을 추가했다. 조합 검토는 정규화한 재료리스트들을 다음의 두가지 검토를 검친다. 첫번째는 정규화된 식재료의 실제 조합검토 ("게"+"감" -> 식중독), 두번째는 특정 성분 식재료 조합검토("탄닌 고함유 식품" + "철분 고함유 식품" -> 철분 흡수 방해)이다. 위험도에 따라서 재료 분석 단계에서 거절하거나 응답때 경고를 표시하도록 설정했다. 두 기능은 llm과 내가 직접 조사한 내용을 토대로 딕셔너리형태로 만들어서 파이썬의 순수로직으로 동작하도록 만들었다. 해당 기능마저 llm으로 구성하기에는 비용이 아깝다고 느껴졌으며, 지난주 카카오 멘토 ahser가 영양성분관련 기능이야기를 할때 DB 이용해서 매칭하는 방식을 추천한데에서 착안해서 두 기능을 개발했다.
- 대화가 계속됨에 따라서 현재 내가 어떤 재료를 넘겨줬는지 잊어서 응답때 추출하고 치환한 재료를 출력하도록 기능을 추가했고, 그에따라 재료 변경,추가,제거 등이 가능하도록 만들었다.
- 현재 해당 프로그램의 문제점은 프리뷰 레시피 단계에서 llm생성과 RAG의 비율이  1:5 로 목록을 제시한다. 하지만 RAG가 충분치 않아 가끔씩 완전 엉뚱한 레시피를 출력한다. 이를 위해 현재 RAG 레시피를 적정성을 검토하는 기능을 어떻게 개발할지 구상중인 단계이다.
- 다음주를 마지막으로 KTB 개인프로젝트를 제출해야하는데 해당 플로우를 기점으로 성능 분석을하고 마무리할 예정이다. 그 이후 멀티 에이전트화와 영양소 기능 연결등은 추후 팀프로젝트를 하면서 기간이 날때 업그레이드 할 예정이다.
