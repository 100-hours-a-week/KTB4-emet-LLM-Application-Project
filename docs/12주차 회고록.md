### 2. 개발 진행상황
#### 2.1. 재료 변경 처리 (기존 재료 추출 방식 확장)
- 사용자가 재료를 추가/제거/교체하려는 의도를 구분해서 처리하도록 확장
- 판단 결과: initial(최초 입력) / add(추가) / remove(제거) / replace(교체)
- 판단과 동시에 이전 턴의 예비 선택지 목록을 초기화하도록 처리
   - 연속으로 레시피 추천을 여러 번 요청할 때 이전 턴 선택지가 섞이던 버그 해결
- action이 remove인 경우와 그 외(initial/add/replace)인 경우를 나눠서 재료 추출
   - remove 전용 추출 노드를 별도로 구현 (제거하고 싶은 재료명만 인식)
- 두 추출 결과를 실제 재료 목록에 반영하는 단계는 LLM 호출 없이 순수 코드로 처리
   - 판단(add/remove/replace)은 LLM, 실행(리스트 병합·제거)은 코드로 역할 분리

#### 2.2. 재료 분석 결과 확장 - 불가 사유 응답
- 기존에는 "생성 불가" 판정 시 이유 없이 미개발 기능 응답으로 처리되던 것을 개선
- 판정 결과에 이유(reason) 필드 추가
   - 재료 수 부족 / 재료 조합이 요리로 성립하지 않음 / 특수 재료 필요 / 먹을 수 없는 재료 포함 등
- 전용 응답 노드 분리
   - "생성 불가"를 더 이상 미지원 기능 응답과 같은 경로로 처리하지 않음
   - 이유를 포함한 정상 응답으로 처리한 뒤 다음 질의를 받는 흐름으로 변경

#### 2.3. 음식 궁합 경고 기능 추가
- 전통적으로 궁합이 안 좋다고 알려진 재료 조합을 감지해서 안내
- 근거가 불충분한 속설(예: 두리안+술, 토마토+설탕)은 별도로 분류해서 오경고 방지
- LLM 호출 없이 순수 코드 매칭으로 구현 (재료 분석 노드 내부에 추가, 비용 부담 없음)

#### 2.4. 재료명 정규화 사전 구축
- 같은 재료를 다르게 부르는 경우(예: 계란/달걀)와 상위/하위 개념(예: 사과/청사과)을 하나로 인식하도록 사전 기반 정규화 도입
- 부족 재료 계산, 재료 추가/제거 판단 양쪽에 공통 적용

#### 2.5. 현재 보유 재료 목록 표시
- 매 응답에 현재까지 파악된 재료 목록을 함께 보여주도록 개선
- 여러 턴에 걸친 대화 중 사용자가 현재 상태를 쉽게 파악할 수 있도록 함

#### 2.6. LLM 폴백 체계 구축
- 기존 단일 provider 호출 구조를 Claude → Google(Gemini) → 로컬 vLLM 순으로 자동 전환되는 구조로 확장
- API 호출 실패나 할당량 초과 시 자동으로 다음 provider로 넘어가도록 구현

#### 2.7. 로컬 vLLM 서빙 환경 구성
- 로컬 GPU가 없는 상황을 대비해 Colab + ngrok으로 vLLM 서버를 임시 구동, 외부에서 호출 가능하도록 연결
- 모델: Qwen2.5

#### 2.8. 배포 인프라 구축
- 도메인 구매 및 EC2 연결 (Elastic IP, DNS 설정)
- GitHub Actions 기반 CI/CD 파이프라인 구성 업데이트
- VDB(ChromaDB)를 S3를 매개로 로컬-EC2 간 자동 동기화하도록 구현
