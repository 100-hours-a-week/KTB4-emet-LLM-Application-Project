## 1. 웹 검색 판정 프롬프트가 "그럴듯하지만 무관한 검색결과"에 낚일 위험

- **증상**: 요리 이름 검색에서 RAG 매칭이 없을 때 웹 검색으로 실존 여부를 판단하게 했는데, 검색 결과 원문을 직접 까보니 "인생네컷도시락", "얼죽아김밥", "핑크뮬리마카롱" 같은 케이스에서 요청한 이름과 무관한 내용(브랜드 콜라보 상품명, 서로 다른 글에서 우연히 언급된 단어 조합 등)이 검색되는데도 표면적으로는 food 관련처럼 보이는 결과가 나옴을 확인.
- **원인**: `generate_recipe_by_name_prompt`가 "검색 결과가 있으면 실존으로 인정"이라는 느슨한 기준이었어서, 이런 무관한 결과를 실존 근거로 오인할 위험이 있었음.
- **조치**: 프롬프트에 "요청한 이름 그 자체를 직접 설명하는 근거인지" 판단하도록 명시하고, 브랜드/서비스명 등 특정 레시피가 없는 경우와 단어 우연 병기 케이스를 명시적으로 비실존 처리하도록 규칙 추가. 애매하면 무조건 비실존(false) 쪽으로 판단하게 함.
- **검증**: 원본 발견 케이스 포함 총 20개 요리명(신조어 트렌드, 흔한 요리, 가상의 이름 혼합)으로 재테스트 → 20/20 기대한 판정과 일치, 오탐 0건. "좀비버거"처럼 애매해 보였지만 실제로는 존재하는 메뉴도 정확히 실존으로 판정.
- 관련 문서: [기능테스트_웹검색_생성판정](기능테스트/20260807_1047_기능테스트_웹검색_생성판정.md), [실제로직테스트_웹검색기반요리실존판정_20케이스](실제로직테스트/20260807_1130_실제로직테스트_웹검색기반요리실존판정_20케이스.md)

## 2. "다른 거 없어?" 재요청이 재추천이 아니라 선택으로 오분류

- **증상**: E2E 20케이스 테스트 중, 재료 추천 목록을 받은 뒤 "다른 거 없어?"라고 물으면 새 추천이 아니라 "목록에 있는 번호나 이름으로 다시 말씀해 주세요"라는 무효 처리 응답이 나옴.
- **원인**: `query_analysis`의 분류 프롬프트(`query_prompt`)가 "다시 보여달라고 하는 등"이라는 모호한 표현으로 '레시피 선택'을 정의하고 있어서, "다른 거 없어?" 같은 재요청까지 '레시피 선택'으로 끌려가 `reset_recipe_options`(재료 흐름 재진입)를 아예 안 타는 문제였음. 그 결과 같은 날 만든 재요청 중복 방지 기능(`shown_rag_ids`/`shown_titles`)도 실제로는 발동 경로에 도달하지 못하는 상태였음.
- **조치**: `query_prompt`에 "다른 거 없어?", "다른 거 보여줘" 등 새로운 선택지를 요청하는 표현은 '레시피 선택'이 아니라 '레시피 추천'으로 분류하라는 규칙을 명시적으로 추가.
- **검증**: 서로 다른 재료 3세트 × 재요청 표현 3종으로 전체 그래프 재테스트 → 3/3 정상 분류, 재추천 목록도 매번 이전과 겹치지 않는 새 요리로 확인.
- 관련 문서: [실제로직테스트_다른거없어_분류수정검증](실제로직테스트/20260807_1313_실제로직테스트_다른거없어_분류수정검증.md)

## 3. `git mv`가 편집 전(스테일) 콘텐츠를 커밋하는 이슈

- **증상**: 테스트 문서들을 `docs/성능테스트/` 폴더로 옮기면서 파일명에 날짜/시각을 붙이고 내용도 일부 보강(전문 복원)했는데, `git mv`로 이동 후 커밋했더니 `git show HEAD:<파일>`로 확인한 실제 커밋 내용이 **편집 전 원본**이었음 (작업 디렉토리 파일 자체는 정상적으로 편집된 상태였는데도).
- **원인**: 정확한 근본 원인은 특정하지 못했으나, `Edit` 도구로 파일을 먼저 수정한 뒤 곧바로 `git mv`로 이동한 경우, 이동 시점에 스테이징되는 내용이 편집 전 커밋 상태를 참조하는 것으로 추정. (재현: 편집 → 즉시 `git mv` → 커밋 → `git show HEAD:<새경로>`가 이전 버전을 보여줌)
- **조치**: 커밋 직후 항상 `git show HEAD:<경로>`로 실제 커밋된 내용을 재검증하는 습관 추가. 이번 건은 발견 즉시 `git add -A` + 재커밋으로 실제 편집 내용을 반영해서 바로잡음.
- **교훈**: 파일 편집과 `git mv`를 같이 하는 작업에서는 편집 → 이동 → 커밋 후 **반드시 `git show HEAD`로 최종 확인**할 것.

## 4. LangSmith trace 조회 스크립트가 KST 시간대로 필터링하면 0건 반환

- **증상**: 특정 시간대(KST 기준)의 LangSmith trace를 다운로드하는 스크립트를 실행했는데, 분명 그 시간대에 실행한 테스트가 있었음에도 `list_runs(start_time=...)` 필터 결과가 매번 0건으로 나옴.
- **원인**: 사용 중인 `langsmith` SDK(0.9.1)의 `list_runs(start_time=...)`가 KST(비-UTC) tz-aware datetime을 넘기면 필터링이 정상 동작하지 않음 — 같은 순간이어도 이를 UTC로 명시 변환해서 넘기면 정상적으로 결과가 나오는 것을 실험으로 확인 (naive datetime도 마찬가지로 실패).
- **조치**: 시간 문자열을 KST datetime으로 만든 뒤 `.astimezone(timezone.utc)`로 UTC 변환해서 `start_time`에 전달하도록 스크립트 수정.
- **검증**: 동일 스크립트로 3개 시간대 재실행 → 각각 69건/26건/21건 정상 발견 및 다운로드 완료.
- 관련 파일: [evaluate/export_langsmith_traces.py](../evaluate/export_langsmith_traces.py)
